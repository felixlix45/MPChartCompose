Architecture Approaches

Three strategies for a high-performance Compose charting library with real-time WebSocket data

A

Canvas-Direct with Snapshot State

Recommended for your use case

All chart rendering happens inside Canvas { } composable using DrawScope. Data flows through Compose's Snapshot system but is read only in the draw phase — no recomposition on data change.

How it handles WebSocket updates:
  1. WebSocket ticks arrive → buffered in a Channel
  2. Frame-synced collector batches ticks per vsync (16ms)
  3. Single atomic state swap triggers draw invalidation only (no recomposition)
  4. Canvas reads new data directly in drawPhase via Modifier.drawWithCache

Pros

  • Zero recomposition on data updates — draw phase only
  • Natural Compose API (DrawScope, Animatable)
  • Frame-batching prevents WebSocket flood
  • Compose animation APIs work natively

Cons

  • Must carefully separate composition vs draw phase
  • DrawScope API slightly less flexible than raw Android Canvas
Performance profile: 60fps with 10K+ points. Draw-phase-only updates. ~0 recompositions during live data streaming.
B

RenderNode + Bitmap Layer Caching

Maximum performance, more complexity

Uses Android's RenderNode (API 23+) for hardware-accelerated layer caching. Static elements (grid, axes, labels) are cached as GPU layers. Only the data layer redraws on updates.

How it handles WebSocket updates:
  1. Chart split into layers: background, grid, data, highlights, labels
  2. Only the data layer invalidates on new ticks
  3. Grid/axes/labels cached as RenderNodes — zero redraw cost
  4. Bitmap fallback for complex paths (like filled area under line)

Pros

  • Fastest possible rendering — GPU layer caching
  • Static layers (grid, axes) never redraw
  • Min SDK 23 = RenderNode available
  • Handles 50K+ points smoothly

Cons

  • Significantly more complex implementation
  • RenderNode API requires careful lifecycle management
  • Mixes Compose and Android graphics APIs
  • Harder to maintain and extend
Performance profile: 60fps with 50K+ points. GPU-cached static layers. Only data layer redraws. Overkill for most stock chart scenarios.
C

Hybrid: Canvas-Direct + Selective Layer Caching

Best balance of performance and simplicity

Starts with Approach A's Canvas-direct rendering as the foundation. Adds lightweight layer separation — grid/axes use drawWithCache (redraws only when axis config changes), data layer redraws per frame. No RenderNode complexity.

How it handles WebSocket updates:
  1. Frame-batched data updates (same as A)
  2. Grid/axes cached via drawWithCache — only rebuild when config changes
  3. Data layer uses onDrawWithContent — redraws per frame
  4. Path caching for line charts — reuse path when only appending points

Pros

  • Clean Compose APIs throughout — no Android graphics escape hatches
  • Grid/axes don't redraw on data changes
  • Path caching reduces draw cost for append-only updates
  • Simple enough to implement and maintain
  • Easy to upgrade to B later if needed

Cons

  • Not as fast as B for extreme datasets (50K+)
  • Still redraws data layer fully (though with path reuse)
Performance profile: 60fps with 10K+ points. Cached static layers via Compose APIs. Path reuse on appends. Upgradeable to RenderNode if needed.

My Recommendation: Option C (Hybrid)

For a stock ticker with WebSocket data, you're likely dealing with hundreds to low-thousands of visible data points — not 50K. Option C gives you the performance headroom you need (60fps easily) while keeping the codebase clean Compose throughout. If you ever hit a wall, the architecture naturally upgrades to B's RenderNode approach without a rewrite.
